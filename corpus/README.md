# Corpus

**These are synthetic documents. Nobody wrote them and nothing in here happened.**

They are generated by `api/scripts/corpus_generate.py` from the seeded database,
and this file's job is to say exactly what that makes the extraction numbers worth.
An earlier version of this file opened with *"Real documents, published with
permission"* — that was the plan until 2026-08-09, and every claim in the repo that
depended on it has been corrected rather than left to age.

    make corpus          # regenerate from the database
    make corpus-verify   # regenerate into a temp dir and assert byte-identity
    make verify-corpus   # checksums, and that nothing unlisted is present

## Generated *from* the database, not alongside it

Every document corresponds to a row, and the row is recorded in `MANIFEST.csv` as
`source_table` + `source_key`:

| Type | Count | Generated from |
|---|---|---|
| Contracts | 24 | one per `supplier_terms` period, including 2 clause-level amendments |
| Invoices | 10 | `purchase_orders` + `purchase_order_lines` |
| Catalogs | 3 | `supplier_prices` on a date |
| Policies | 3 | free-standing — the only type with no row behind it |

**This is the property that makes the temporal demo honest.** "What were the terms
before the renegotiation?" is answerable from the documents *and* checkable against
`supplier_terms`, because the document was made from that row.

> ### ⚠️ There are no coverage gaps, and this file used to say there were

Invoice totals reconcile against `sum(line_total)` for the same order, so a
mis-extracted line item is *detectable* rather than merely wrong.

## What the difficulty in here is, and what it is not

**Every hard case was chosen by us.** That is the central limitation and no number
in this repo should be read without it. Ten of the 40 documents carry an injected
property, listed per document in `MANIFEST.csv`:

| Property | Documents | What it tests |
|---|---|---|
| `scanned-200dpi-skewed` | 4 | **No text layer at all.** Rasterised, rotated by a fraction of a degree, blurred, speckled, JPEG'd. Forces OCR, which is where extraction accuracy is actually decided. |
| `table-spans-page-break` | 2 | A line-item table continuing across a page boundary |
| `totals-above-line-items` | 1 | A supplier template where the total precedes the rows it summarises |
| `clause-level-amendment` | 2 | A document that varies three clauses of an earlier agreement and restates nothing else |
| `signature-block` | 2 | A signature area below the content |

**So the measurement says: the pipeline handles the failures we thought of.** That
is a real and useful thing to measure, and it is a weaker claim than surviving
documents nobody designed. Where a real corpus would have produced difficulty we
had not anticipated, this one cannot.

Every one of those properties is **re-derived from the rendered PDF** by
`verify_difficulty()` before the manifest is written, and generation fails if a
document does not exhibit what it advertises. That check exists because the first
run produced a manifest claiming a page-break table on a single-page invoice —
a row advertising a test that did not exist.

### One difficulty was attempted and dropped

**`bilingual-mr-en` is defined, rendered, verified — and assigned to nothing.** The
build environment has no Devanagari font (only DejaVu, which does not cover the
script), so the Marathi text rendered blank and the verification refused the run.
Transliterating into Latin script would have produced a document carrying the label
without the difficulty.

**The pipeline is therefore not tested on non-Latin scripts.** For a Maharashtra
chain that is a real gap, not a rounding error. Installing a Devanagari font and
putting the mark back on a contract closes it.

## PII

**The scan is vacuous here and must not be reported as a result.** It existed
because real records carry home addresses, phone numbers, bank details and ID
numbers; generated documents carry none unless a generator writes them, and this
one writes supplier contact addresses that are already in the seeded `suppliers`
table and are themselves synthetic.

It is kept as a standing check on one specific thing: that the generator never
invents anything person-like. `sale_operators` already forbids person-like staff
names for the same reason — the agent reports patterns, never people (ADR-0002).
**A check that cannot fail is not evidence that it passed**, so this section says
what it is instead of publishing a number.

## Reproducibility

`make corpus` twice produces byte-identical output, asserted by `make
corpus-verify`. Getting there was not free, and the two causes are worth knowing
because both are silent:

- **reportlab** stamps `CreationDate`/`ModDate` from the wall clock and gives each
  document a random `/ID`. Pinned via `invariant=1` and fixed metadata.
- **PyMuPDF** regenerates the second `/ID` element on every save, because the PDF
  spec says it changes when a file is modified. That was the *only* varying byte —
  31 of them, in the trailer, in all 40 documents. `no_new_id=True` fixes it, and
  it is undocumented in this version: absent from `save.__doc__` and from the
  signature, but accepted. Passing it on the intermediate save too is not
  redundant — it *preserves* an existing ID rather than suppressing one, so
  without it the four scanned documents still varied after the other 36 were
  fixed.
